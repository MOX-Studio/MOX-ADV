# Codebase Concerns

**Analysis Date:** 2026-08-22

## Tech Debt

**Large authority/orchestrator modules:**
- Issue: several modules concentrate thousands of lines and multiple transition families.
- Files: `sites/p0-production/lib/p0-application.ts` (~3419 lines), `src/mox_adv/control_state.py` (~2332), `src/mox_adv/ui_service.py` (~2286), `src/mox_adv/campaign_lifecycle.py` (~1957), and `src/mox_adv/yandex_read.py` (~1829).
- Impact: reviews must reason about broad state surfaces; unrelated changes can collide, and hidden coupling is easier to introduce.
- Fix approach: preserve each existing public authority but extract focused pure validators, projections, repositories, and command handlers behind narrow interfaces with characterization tests.

**Generated Python package metadata is tracked:**
- Issue: `src/mox_adv.egg-info/` is generated by editable/build installs but committed as source.
- Impact: package metadata can drift from `pyproject.toml` or produce noisy unrelated diffs.
- Fix approach: remove generated egg-info files from version control, ignore `*.egg-info/`, and generate them during installation.

**SQLite schema evolution is distributed:**
- Issue: many Python stores create/evolve tables inline in modules such as `control_state.py`, `campaign_lifecycle.py`, `goal_store.py`, `monitoring.py`, and `ui_automation.py`.
- Impact: compatibility and migration behavior must be rediscovered per store; cross-store upgrades are hard to audit as one release operation.
- Fix approach: document schema versions/migrations per store and add restart/upgrade fixtures before changing any persisted table.

**P0 environment typing is incomplete:**
- Issue: `sites/p0-production/cloudflare-env.d.ts` declares D1 plus core Direct/Metrika values, while `lib/p0.ts` also accesses Wordstat, currency/VAT, campaign, and comparable-evidence bindings through a broad `Record<string, string | undefined>` cast.
- Impact: misspelled or omitted production bindings evade TypeScript checks and fail only at runtime.
- Fix approach: enumerate every runtime binding in `Cloudflare.Env`, derive adapter config from that typed object, and test missing/invalid binding diagnostics.

## Confirmed Setup Defect

**README references an ignored, untracked `.env.example`:**
- Symptoms: `README.md` instructs `cp .env.example .env`, but `.env.example` is not tracked.
- Trigger: clone the repository and follow the documented local binding setup.
- Root cause: `.gitignore` first negates `!.env.example` but later ends with `.env*`, which re-ignores the template.
- Workaround: create the four documented variable names manually without values.
- Fix: move the negation after the final `.env*` rule and commit a secret-free `.env.example`.

## Security Considerations

**Unauthenticated shared root demos are intentionally non-production:**
- Risk: the Vercel demo and temporary tunnel expose shared Dashboard state; `VercelPublicDemoAuthenticator` represents a fixed demo identity, and all visitors share the same state.
- Files: `README.md`, `api/index.py`, `src/mox_adv/vercel_runtime.py`, and `scripts/mox-adv-demo-site`.
- Current mitigation: explicit demo labeling, loopback origin before tunneling, read-only Yandex production mode, fake write targets, and on-demand URLs.
- Recommendation: never promote this surface as a multi-user production control plane; add real authentication, tenant isolation, authorization, CSRF controls, and per-user state first.

**Credential/channel boundaries are duplicated across root and P0:**
- Risk: root Keychain/protected-dotenv policy and P0 Worker environment bindings are separate implementations with different write capabilities.
- Files: `config/gate0-policy.json`, `src/mox_adv/yandex_read.py`, `sites/p0-production/lib/p0.ts`, and `sites/p0-production/lib/direct-write.ts`.
- Current mitigation: the P0 candidate is intentionally isolated from the Integrated Prototype; credentials stay server-side and tests strip production variables.
- Recommendation: keep the isolation explicit until P0 acceptance is complete; do not share a generic Yandex client that could accidentally widen root read-only capability.

**P0 Direct fetches lack a visible common timeout wrapper:**
- Risk: provider calls in `sites/p0-production/lib/direct-write.ts` and several `lib/p0.ts` context readers use injected/global fetch directly; a stalled provider can hold a request or account lease longer than intended.
- Current mitigation: durable intent/journal rows, account leases, reconciliation semantics, and platform request limits.
- Recommendation: add a shared abort-aware timeout wrapper and tests that prove timeout classification, lease handling, and no blind retry.

## Performance and Scaling Limits

**Root Vercel state snapshots copy the complete run tree:**
- Problem: every stateful API request can restore and later zip/upload the entire `runs/` tree.
- Files: `api/index.py` and `src/mox_adv/vercel_runtime.py`.
- Current bound: compressed and expanded archives are capped at 64 MiB; synchronization is process-local.
- Impact: latency and race risk grow with accumulated run artifacts and multiple function instances.
- Improvement path: keep this as a bounded demo mechanism or migrate durable shared state/artifacts to transactional records/object-per-artifact storage before production scale.

**Local Dashboard concurrency is intentionally narrow:**
- Problem: `src/mox_adv/ui_server.py` uses `ThreadingHTTPServer` over multiple SQLite stores, while some critical writes rely on short SQLite timeouts and process-local locks.
- Impact: suitable for one operator/demo, not an unbounded multi-user service.
- Improvement path: retain single-operator scope or introduce a real application server and transactional shared database with tested locking semantics.

**Whole-document P0 revisions can grow:**
- Problem: D1 stores the full `P0Document` JSON for current state and each immutable revision in `sites/p0-production/db/schema.ts`.
- Impact: document size, history reads, and migration costs grow together as evidence/package history expands.
- Improvement path: keep bounded arrays/artifacts, measure document/revision size, and split large immutable evidence into content-addressed records only if measurements justify it.

## Fragile Areas

**Root Gate 0 API/authority matrix:**
- Why fragile: `config/gate0-policy.json` is large and consumed by transport, authorization, monitoring, campaign, goal, and E2E logic.
- Common failures: schema/value drift can silently change which operation or principal is legal if not validated everywhere.
- Safe modification: update `scripts/validate_gate0.py`, `tests/test_validate_gate0.py`, transport matrices, and acceptance fixtures together; preserve `production_write_authorized: false` for the root application.

**P0 document migrations and truth table:**
- Why fragile: `sites/p0-production/lib/p0-application.ts` migrates many legacy document schemas while also owning current commands and downstream invalidation.
- Common failures: migration can reconstruct invalid lineage, stale revisions can regain authority, or UI availability can diverge from command legality.
- Safe modification: keep one truth table, reject unknown/same-schema drift, add old-document fixtures, and test every material invalidation cascade.

**Provider semantic readback and moderation:**
- Why fragile: Direct add/update success is not enough; P0 must preserve IDs, suspension, child graph, moderation, ownership, and correction lineage.
- Files: `sites/p0-production/lib/direct-write.ts`, `execution-safety.ts`, and `campaign-package-execution.ts`.
- Safe modification: maintain provider-shape contract tests for partial failures, ambiguous outcomes, restart recovery, independent item continuation, and the permanent absence of `Campaigns.resume`.

**Integrated Prototype versus P0 boundary:**
- Why fragile: both surfaces model campaigns but have different authority and deployment assumptions.
- Current contract: `README.md` says the P0 module is absent from `/prototype/mox-adv` until refinement and E2E acceptance are complete.
- Safe modification: integrate only through the authoritative `mox-adv.p0.application` query/command contract; never copy P0 presentation-derived state into the Python Dashboard.

## Dependencies at Risk

**vinext beta runtime:**
- Risk: `vinext` is pinned to `1.0.0-beta.2`, so build/runtime behavior can change sharply between upgrades.
- Impact: P0 routing, React Server Components, Cloudflare integration, or dev-server behavior may break.
- Mitigation: exact npm lockfile, build-before-test, and dedicated `vite-watch`/rendered HTML/E2E tests.
- Upgrade approach: change one pinned runtime set at a time and run `npm run lint`, `npm run test:contract`, and P0 E2E.

**Two deployment stacks:**
- Risk: the Python Vercel demo and OpenAI Sites/Cloudflare P0 candidate have different storage, auth, and runtime contracts.
- Impact: a feature can pass in one stack and remain unavailable or unsafe in the other.
- Mitigation: explicit module separation and stack-specific E2E; keep deployment documentation clear about which surface is authoritative.

## Test and Delivery Gaps

**No automated test CI:**
- Gap: `.github/workflows/` contains only `deploy-dashboard-demo.yml`; no push/PR workflow runs Python tests, P0 build/tests, or ESLint.
- Risk: main can receive code that fails one runtime or safety boundary without a repository-hosted gate.
- Priority: high.
- Fix approach: add separate deterministic jobs for Python unit/integration tests and P0 lint/build/Node contracts; keep browser/Docker suites opt-in or scheduled if runtime cost is high.

**No numeric coverage visibility:**
- Gap: neither root nor P0 scripts generate or enforce line/branch coverage.
- Risk: the large boundary matrix may still hide unexercised branches, especially in migrations and error handling.
- Priority: medium; percentage alone must not replace semantic safety tests.
- Fix approach: report coverage for visibility, then set targeted expectations on safety-critical modules after establishing a baseline.

**Very large test modules:**
- Gap: `tests/test_review_regressions.py` (~2384 lines) and `sites/p0-production/tests/p0-application-contract.test.mjs` (~3215 lines) combine many regressions.
- Risk: fixture coupling and failure diagnosis become expensive; parallel ownership is difficult.
- Fix approach: split by stable contract capability while sharing builders through explicit test-support modules.
