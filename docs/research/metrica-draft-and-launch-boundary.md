# Граница Яндекс Метрики между Campaign Draft и публикацией

**Дата проверки источников:** 2026-08-31
**Контекст:** финальное решение Wayfinder «Утвердить целостный контракт прозрачного пайплайна Campaign Draft»
**Вопрос:** должна ли подтверждённая Яндекс Метрика блокировать формирование полного Campaign Draft, если текущий модуль только создаёт, показывает и редактирует шаблоны кампаний?

## Краткий вывод

Подтверждённая Метрика **не должна быть универсальным предусловием формирования Campaign Draft**.

Официальный контракт Direct API допускает создание ЕПК без `CounterIds` и `PriorityGoals`: оба параметра необязательны. Стратегия `WB_MAXIMUM_CLICKS` требует ограничение бюджета, но не `GoalId`. Напротив, стратегии, оптимизирующие конверсии или их стоимость, требуют точную цель Метрики.

Поэтому обязательность Метрики должна зависеть от выбранной стратегии и утверждений результата:

1. **Для полного Draft с `ЕПК / Поиск / WB_MAXIMUM_CLICKS`:** достаточно доказанного предложения, аудитории, посадочной, спроса, географии, периода, бюджета и полной технической проекции. `CounterIds`, `PriorityGoals`, историческая воронка, CPA и прогноз конверсий могут отсутствовать. Неизвестное не подменяется идентификатором, нулём или оценкой.
2. **Для Draft со стратегией, зависящей от конверсий:** точные счётчик и цель обязательны для этой конфигурации. Без них агент выбирает допустимую бюджетно-ограниченную альтернативу либо возвращает точный запрос, если альтернативная стратегия противоречит бизнес-решению.
3. **Для анализа компании:** доступная read-only Метрика усиливает Evidence Snapshot, но отсутствие чужой приватной истории означает только `UNAVAILABLE` для этого семейства доказательств. Оно не блокирует анализ по разрешённым общедоступным источникам.
4. **Перед реальной публикацией:** последующий модуль выполняет свежий account-specific preflight. Если точная проекция использует цель или конверсионную стратегию, он обязан подтвердить binding и работоспособность цели. Текущий модуль не публикует кампании и не расходует бюджет.

Это сохраняет строгую измеримость там, где она действительно используется, но не превращает закрытые данные чужого рекламодателя в обязательное условие создания изучаемого шаблона.

## Первичные источники и установленные факты

### 1. Счётчики и приоритетные цели необязательны в контракте создания ЕПК

В официальной схеме `Campaigns.add` для `UnifiedCampaignAddItem`:

- `CounterIds` имеет `Required: No`;
- `PriorityGoals` имеет `Required: No`;
- `CounterIds` описывает идентификаторы счётчиков, установленных на сайте;
- `PriorityGoals` задаёт цели для автоматической корректировки ставок.

Источник: [Direct API — `add: UnifiedCampaign parameters`](https://yandex.com/dev/direct/doc/en/campaigns/add-unified-campaign), раздел `UnifiedCampaignAddItem structure`.

Следствие: отсутствие доступа к счётчику не делает API-проекцию ЕПК структурно неполной само по себе.

### 2. `WB_MAXIMUM_CLICKS` не требует цели Метрики

Та же официальная схема разделяет параметры стратегий:

- `WbMaximumClicks` требует `WeeklySpendLimit` либо бюджет на период и не содержит обязательного `GoalId`;
- `WbMaximumConversionRate`, `AverageCpa`, `PayForConversion`, `AverageCrr` и `PayForConversionCrr` используют обязательный `GoalId` в соответствующих конфигурациях.

Источник: [Direct API — `add: UnifiedCampaign parameters`](https://yandex.com/dev/direct/doc/en/campaigns/add-unified-campaign), структуры `StrategyMaximumClicksAdd`, `StrategyMaximumConversionRateAdd`, `StrategyAverageCpaAdd`, `StrategyPayForConversionAdd` и связанные структуры.

Официальная справка описывает «Максимум кликов» как стратегию получения максимума переходов при ограничении средней цены клика или бюджета. Источник: [Яндекс Директ — «Максимум кликов»](https://yandex.ru/support/direct/ru/strategies/average-cpc).

Следствие: бюджет является обязательным экономическим входом для выбранного профиля; `target_result_cost` и цель Метрики обязательны только для зависящих от них стратегий или claims.

### 3. Метрика необходима для конверсионной оптимизации, а не для любого Campaign Draft

Официальная справка «Максимум конверсий» требует счётчик и цели и объясняет, что стратегия использует накопленные данные для прогнозирования конверсионности и назначения ставок.

Источник: [Яндекс Директ — «Максимум конверсий»](https://yandex.ru/support/direct/ru/strategies/average-cpa).

Следствие: нельзя выбирать конверсионную стратегию, придумывать `GoalId`, CPA или конверсионную историю при отсутствии точного измерительного контура. Ограничение относится к конкретной strategy projection, а не ко всему этапу подготовки кампаний.

### 4. Данные чужой Метрики действительно приватны

Яндекс позволяет владельцу счётчика дать пользователю Директа разрешение использовать цели для оптимизации **без доступа ко всему счётчику**. При таком разрешении доступны только сведения, необходимые для работы конкретной кампании; пользователь не получает полную прошлую статистику чужого счётчика.

Источник: [Yandex Direct — “Yandex Metrica: evaluate your promotion performance”](https://yandex.com/support/direct/en/statistics/metrika.md), раздел о доступе к целям без доступа к tag.

Следствие: публично видимый сайт или номер счётчика не дают права читать каталог целей, историческую воронку и отчёты. Отсутствие таких прав должно честно давать `UNAVAILABLE`, а не запускать scraping, запрос ручного provider ID или восстановление скрытых показателей.

### 5. Используемая цель должна быть проверена

Официальная инструкция проверки цели требует выполнить целевое действие, увидеть событие в отладчике и убедиться, что конверсия отражается в отчёте. Если событие не появляется, цель не регистрируется.

Источник: [Яндекс Метрика — “Checking a goal”](https://yandex.ru/support/metrica/en/general/check-goal).

Следствие: наличие объекта цели или похожего названия недостаточно для конверсионной стратегии. Проверка регистрации является обязательным preflight для проекции, которая действительно потребляет эту цель.

## Рекомендуемый продуктовый контракт

### Публичный анализ внешней компании

Для ИННОПРОМ и других компаний, не предоставивших read-only доступ:

- Evidence Analyst автоматически использует разрешённые публичные первичные источники, сайт, Wordstat, официальные реестры и допустимые публичные наблюдения;
- приватные Direct/Metrica evidence families получают `UNAVAILABLE_NO_AUTHORITY`;
- отсутствие приватных данных не трактуется как нулевые кампании, нулевой трафик или нулевые конверсии;
- Strategy Agent не делает утверждений о фактическом CPA, конверсии, рекламной эффективности или внутренней структуре кампаний компании;
- Campaign Design Agent формирует полный Draft только в профиле, не требующем неизвестной цели, например `ЕПК / Поиск / WB_MAXIMUM_CLICKS`, с явным пределом бюджета;
- `CounterIds` и `PriorityGoals` отсутствуют как неприменимые необязательные поля, а не заполнены placeholder-значениями;
- UTM/naming contract и будущая точка измерения могут быть предложены, но не выдаются за уже подключённую Метрику.

### Подключённый рекламодатель

Если рекламодатель предоставляет официальное read-only право:

- Evidence Analyst обнаруживает и проверяет exact counter/goal через Management API;
- историческая воронка остаётся отдельным необязательным evidence contour: `RARE`, `PARTIAL`, `STALE` или `UNAVAILABLE` ограничивает claims, но не подменяет работоспособность binding;
- Campaign Design Agent может выбирать goal-dependent strategy только при выполнении её точных требований;
- каждое consumed measurement field сохраняет lineage к binding и версии проверки.

### Граница будущей публикации

Будущий модуль публикации обязан заново проверить:

- точный Direct account и его capabilities;
- права внешней записи;
- актуальность `publish_fingerprint`;
- обязательные параметры выбранной стратегии;
- exact counter/goal и регистрацию события, если проекция их использует;
- отсутствие подмены evidence из публичного анализа приватными фактами.

Решение человека разрешает внешнюю запись только точного прошедшего preflight отпечатка. До этого момента Dashboard показывает шаблон и его происхождение, но не состояние `APPROVED_FOR_PUBLICATION`.

## Что сохраняется из прежнего контракта Метрики

Сохраняются:

- только официальные API и запрет браузерного кабинета;
- protected provider bindings и запрет показывать provider IDs владельцу;
- разделение exact measurement binding и исторической воронки;
- проверка тестового события для реально используемой цели;
- sampling/privacy/lag/freshness и запрет причинных claims;
- точечная инвалидация по consumed claim refs;
- компактная карточка Метрики и очищенный системный след.

Изменяется одно правило: `measurement_binding.status=VERIFIED` больше не является универсальным обязательным input для любого Campaign Draft. Оно является условным обязательным input только для проекции и утверждений, которые используют Метрику.

## Проверочные сценарии

1. **Внешняя компания, только публичные данные:** полный `ЕПК / Поиск / WB_MAXIMUM_CLICKS` Draft без `CounterIds`, `PriorityGoals`, CPA и конверсионных claims.
2. **Нет Метрики, но предложена conversion strategy:** стратегия не компилируется; агент выбирает допустимый maximum-clicks fallback либо запрашивает одно материальное решение.
3. **Есть разрешение на цель, но нет полной истории:** goal-dependent projection допустима только после exact binding/test-event preflight; историческая воронка остаётся `UNAVAILABLE` и не блокирует сама по себе.
4. **Есть полный read-only доступ:** binding и допустимая историческая аналитика входят в Evidence Snapshot и влияют только через явные зависимости.
5. **Цель существует, но тестовое событие не регистрируется:** goal-dependent projection блокируется; неизвестное не заменяется другой целью.
6. **Будущая публикация:** перед внешней записью повторно проверяются account capabilities, права, exact goal requirements и fingerprint.

## Решение для Wayfinder

Целостный пайплайн должен различать:

- **полноту Campaign Draft** по выбранному поддерживаемому API-профилю;
- **доступность приватного аналитического evidence**;
- **допустимость конкретной bidding strategy**;
- **готовность к будущей внешней публикации**.

Объединять эти четыре понятия в один общий Metrica gate — неверно. Условные требования выбранной стратегии дают более точную, честную и реализуемую границу.
