# MOX-ADV P0 production candidate

Local production candidate for the first MOX-ADV campaign workflow.

The provider-neutral `P0AgentRuntime` owns one bounded `COORDINATE_OWNER_JOURNEY` objective. It plans only application-published typed tools: bounded reads, the durable Direct audit, one application-selected due-work continuation, and dispatch already bound to an exact persisted Human Decision Gate; generic HTTP, browser, SQL, shell and raw provider RPC are absent. `lib/p0-application.ts` owns schemas, permissions, freshness, authority, Critical Decision/Material Uncertainty classification and final truth. Public content and every tool observation remain evidence and cannot mutate that control plane. Runs, checkpoints, observations, source references and model/tool/token/active-time/cost budgets persist in D1. Queued reports resume automatically after their persisted due time in a fresh runtime and compact prior observations without owner retry controls. The owner page and `POST /api/p0/agent` receive only bounded Agent Activity, Finding, Problem or prepared Human Decision Gate progress; runtime identities, tool names and technical continuation controls stay outside that surface. `lib/p0-application.ts` keeps its deterministic business-model extractor explicitly labelled `DETERMINISTIC_EVIDENCE_EXTRACTOR`; it is baseline evidence processing, not the neural-agent runtime.

Access Readiness verifies Direct read scope through official `clients.get`; when Yandex returns the documented Direct-Pro-only error, it may instead confirm only the exact server-configured advertiser and campaign through bounded `Campaigns.get`. That fallback restores legacy read access but never fabricates client capabilities or publication authority: the Context publication preflight still requires the exact Direct capability snapshot. The exact Yandex Metrika counter and goal are verified through official Management APIs before private evidence is used. Its Direct read continues through every `LimitedBy` page for campaigns, groups, audience criteria, keywords/autotargeting, ads and referenced supported assets. Exact campaign and search-query Reports requests are persisted before dispatch; HTTP 201/202 state and provider `retryIn` timing resume without new authority. Full provider pages and TSV reports live only in separate D1 audit artifacts, while application/model/UI surfaces receive the validated sub-64 KB business summary and artifact references. Partial permissions, warnings, rate limits, current provider limitations and exact 64-bit IDs remain evidence; browser cabinets are never used. Context then researches only a DNS-verified public first-party HTTPS target with manual redirect handling, a four-redirect cap, at most six pages and a 5 MB streamed-response budget. Private/local/link-local resolutions, credential-bearing URLs, cross-party redirects and oversized responses fail closed. Before the longer Model analysis starts, the step persists the sanitized API/site facts and exactly one evidence-grounded provisional business goal; the owner must explicitly confirm or correct it.

The application keeps all OAuth credentials server-side and persists revisioned state in D1. Exact package dispatch creates one deterministic durable execution identity per selected Draft and runs those item executions independently under one account-level writer lease. Each item records validation, creation, exact suspension, child graph, semantic readback, moderation, provider IDs/issues, ownership and containment. Moderation is polled by a separate bounded command: the document persists each poll attempt, observation and `next_poll_at`, so no request waits for terminal moderation. `MODERATION`, `PREACCEPTED`, unknown and reconciliation states keep the verdict `PENDING`; only final `ACCEPTED` ads can satisfy group coverage. `PASS` requires every selected campaign to retain its complete supported graph, final `State=SUSPENDED`, at least one accepted ad per group and a terminal visible outcome for every additional ad. Fully accounted provider rejections may produce `PASS_WITH_PLATFORM_REJECTIONS`; no initial acceptance or any system-owned failure produces `FAIL`. Definite contained provider or system failures do not erase or stop later safe items; ambiguous outcomes hold the account boundary and leave the remaining items queued. A fully-accounted moderation rejection can open one focused correction linked to the immutable initial package hash, item snapshot, StatusClarification, provider issues and exact Draft. Only a material editable-field delta creates the corrected Draft revision/fingerprint and fixed-membership rescore. It then requires a new one-item package review and a prepared Human Decision Gate that presents the recommendation, evidence, confidence, alternatives, and consequences before the existing suspended provider graph is updated through official `Campaigns.update`, `AdGroups.update`, `Keywords.update` or `Ads.update` only for object kinds named by the field-level delta, semantically read back and resubmitted through `Ads.moderate`. Unknown and reconciliation-required outcomes never enter correction. Corrected success is accounted separately as `PASS_AFTER_CORRECTION`; it never rewrites the initial package verdict or counts initial generation as passed. Every mutation body and fingerprint is journaled before its network call, bounded recovery uses only the exact item fingerprint and known provider IDs, and no write is blind-retried. The semantic readback rules are documented in [`docs/direct-provider-normalization.md`](../../docs/direct-provider-normalization.md). The Model step also presents a permanently labelled `ADVISORY · NON-BLOCKING` LandingAdvisoryRun for the exact approved Campaign Strategy revision and normalized final landing URL. The versioned injected audit harness requires Lighthouse `12.8.2`, Chrome `136.0.7103.113`, desktop config `p0-lighthouse-desktop-1920x1080-v1` and axe-core `4.10.3`; it records exactly five sequential 1920×1080 Lighthouse attempts and component medians only when all five succeed, plus bounded raw axe category counts/details and explicit incomplete/manual review. Its fail-closed browser policy permits credential-free GET/HEAD only to exact public first-party allowlisted hosts after DNS/IP checks, binds every connected request address back to that public resolution to prevent DNS rebinding, denies restricted/auth/admin paths and cross-party subresources, and disables clicks, forms, uploads, downloads, cookies and client storage. Every injected adapter operation receives a 30-second AbortSignal and must settle after cancellation before the harness starts the next sequential operation. Persisted observations are bounded and redacted. Observed Metrika behavior is copied only from the exact counter/goal evidence already persisted by official APIs; missing, partial or zero-visit coverage remains insufficient. Findings are typed `OBSERVED_FACT`, `DETERMINISTIC_CHECK` or visibly non-authoritative `LLM_HYPOTHESIS`. The run is a separate top-level advisory artifact and is never an input to eligibility, publish readiness, score, rank, thresholds, calibration or the canonical publish fingerprint. Deployments without the pinned injected browser runtime persist and render explicit insufficient evidence instead of claiming an audit.

The Model step first persists a compact `p0-business-model-v1` owner contract. Its qualified outcome, customer and buying context, revenue model, sales cycle, value/margin and lead-to-sale inputs, capacity, seasonality, geography, exclusions and constraints each retain availability, provenance, observation time, freshness, confidence/limitation and an explicit assumption slot. The owner edits those business facts through the typed journey; unknown values remain unavailable and generate only material questions. Target result cost is deterministically derived from owner-confirmed sale value × gross margin × lead-to-sale rate, otherwise economics remains a Material Uncertainty that hard-blocks eligibility regardless of any positive budget or manually supplied target. Content-addressed Model revisions make normalization-only saves exact no-ops, while any material Model or economics change invalidates Strategy and every downstream decision lineage.

The Model step then persists a bounded `p0-offer-catalog-v1` of materially distinct offer clusters. Outcome, audience, economics, destination or offer changes create separate catalog entries, while close SKU labels with identical material axes merge with retained provenance. The linked `p0-focus-opportunity-set-v1` keeps market opportunity, launch readiness and evidence coverage separate, recommends only a defensible launch-now focus, preserves nearest alternatives and blocked/insufficient options, and emits one prepared Product Focus Human Decision Gate for a material tie or unstable recommendation. `select_focus` creates a content-addressed Product Focus revision; a material owner change invalidates Strategy, Recommendation Set, Campaign Drafts, shortlist and package authority before rebuilding evidence. The business-facing Model projection renders these dimensions and the prepared decision packet without exposing internal offer, recommendation, evidence or revision IDs.

The Model step emits one deeply immutable, content-addressed `p0-analytics-evidence-v6` snapshot with separately hashed source manifests, normalized claims, typed Evidence Records, a separately hashed bounded competitor matrix, bounded/redacted raw locators and values, transforms, versions, timestamps, conflicts and explicit gaps. Its hashed domain manifest indexes the business model, Direct, Metrika, Wordstat, comparable cost and competitors inside that single authoritative snapshot; every claim resolves through its Evidence Records to exact source manifests, freshness, confidence and explicit limitations, while each domain retains its claim, evidence, conflict and gap lineage. A separate hash-verified `p0-analytics-evidence-lifecycle-v1` ledger stores only version references and comparison semantics, never a second copy of analytics: unchanged requests reuse the active content address, while a material Context, Model, Product Focus or competitor-evidence change links the previous and replacement snapshot, records affected domains and names every dependent result whose authority was cleared. First-party public observations, owner confirmations, official Direct API evidence, official Metrika API evidence and allowlisted public competitor observations remain distinct. Confidence stays a quality/freshness/consistency/coverage/uncertainty vector; Metrika sampling/privacy/lag and Direct read limitations remain attached, and unavailable current Direct inventory is a material blocker rather than zero activity. Competitor research now requires a finite candidate set with one business rationale and one to three exact public HTTPS destinations per candidate. Credential-free reads fail closed before DNS/fetch for non-allowlisted URLs and fail closed on redirect or cross-host drift. Every matrix row preserves products/services, observed offer/message, published price or explicit absence, exact landing/source, geography/device scope, observation time and ad-visibility sample; aggregate claims preserve the candidate-set rule, denominator and observed count. Missing rows and samples remain unavailable rather than zero, prompt injection and hidden spend/CPC/conversions/CPA/ROI/profitability/account-state/internal-strategy claims are rejected, and public visibility remains observation rather than effectiveness. The same snapshot now persists one bounded typed multi-seed research plan across offer language, customer problems, high-intent actions, brand/non-brand formulations, exclusions, explicit regions/devices and monthly seasonality. It collects official Wordstat `/v1/topRequests`, `/v1/dynamics` and `/v1/regions` observations under one batch identity with method/operator/scope lineage; unique assigned rows are summed once and labelled `LOWER_BOUND_OBSERVED_TOP_ROWS`, while missing rows, partial responses, quota and provider failures remain `PARTIAL`/`UNAVAILABLE`, never zero. Comparable cost candidates are discovered automatically from the completed durable Direct graph and search-query report artifacts—owners never supply keyword IDs—and must match phrase, exact region set, Search placement, `WB_MAXIMUM_CLICKS`, current audit window and minimum click sample before any official `KeywordBids.get` or own-history range is used. Pre-launch cost selects one qualified source-labelled range without averaging; no qualified source remains explicitly unavailable. Snapshot, trusted agent summary and owner projection retain source/date/currency/VAT/sample/business scope while provider object IDs remain internal to the transient qualification/read boundary. The owner analytics summary renders six business areas with separate finding, source, freshness, confidence and limitation states; it never collapses partial, stale, conflicting or unavailable evidence into false readiness, and orders repairs first by campaign admissibility, then Strategy impact, then confidence. The Strategy step persists one versioned questionnaire with exactly 12 typed fields in canonical order: business goal, campaign focus, advertised offer, target audience, qualified result, exclusions, geography, period, landing page, weekly budget, target result cost and core message. Every row has exactly one recommendation (explicitly `null` when unsupported), a short operator explanation, one allowed source category and one simple status. Unknown geography, period and business-owned economics remain prepared decisions with consequences; Direct minimums and pre-launch cost evidence are constraints, never invented budget or target-cost defaults. The owner first saves normalized answers as one immutable review candidate; a separate screen places the full Strategy beside evidence, alternatives and limitations. Only `CONFIRM_EXACT_CAMPAIGN_STRATEGY` records one explicit confirmation bound to the exact Business Model, Product Focus, Analytics Evidence and Strategy versions and then opens Campaign Drafts. Rejection returns the same saved values to editing, stale review handles fail closed, and any material edit immediately removes the prior confirmation and closes Campaign Drafts until a new exact version is reviewed; normalization-only edits preserve the accepted version. Campaign Strategy then compiles persisted Demand Clusters into deterministic delivery buckets across goal, economics, geography, landing, message and management; compatible long-tail is packed, while a material split requires evidence-backed standalone capacity. The authoritative `campaign-fanout-v1` compiler evaluates the finite product × audience × offer × keyword-cluster ledger exactly once, emits one comparator plus at most two one-factor improvements per bucket, and stores a visible/hidden terminal audit record for every Draft or excluded rule candidate. Competitive naming requires the accepted versioned sample rule; otherwise the comparator is exactly `STRATEGY_BASELINE_FALLBACK`. A publishable new Draft must pin one injected, persisted `ACTIVE` + `APPROVED` content-addressed curated playbook release and only its exact applicable rules; stale, expired, quarantined, contradicted, deactivated, superseded, malformed, unapproved and unknown-version inputs are excluded fail closed. The production default supplies `p0-curated-playbook-v1`, curated from the accepted #149 decision and the linked official Yandex Direct source. Its material rule records exact applicability, observation/review/expiry dates, conflicts, exceptions and an executable eval fixture; its lineage includes release and rule content digests. Pre-launch observations, owner edits and moderation outcomes have no admission path and cannot create a rule or expand policy, capability or execution authority. The core capability profile is fixed to Direct v501 `UNIFIED_CAMPAIGN` / `UNIFIED_AD_GROUP`, Search `WB_MAXIMUM_CLICKS`, Network `SERVING_OFF`, explicit keywords and `TEXT_AD`. Conditional provider fields require persisted official API plus exact-account eligibility evidence; unsupported selected fields remain in the attempted projection, produce an explicit publication blocker and are never silently dropped. Draft identity pins Strategy/Draft revisions, capability profile ID/version and playbook release/rule lineage; the `sha256:` publish fingerprint canonicalizes only provider-declared unordered arrays and preserves ordered-array semantics. A material Strategy edit creates a new revision, regenerates the finite Recommendation Set and clears Draft/shortlist lineage, while whitespace and URL normalization preserve it. Material Context or Model edits invalidate downstream lineage; the UI discloses that cascade and both the contract and UI block confirmation while persisted recomputation is pending. Every mutation uses document-level `expected_revision` compare-and-swap, so stale tabs fail closed without field-level merging. After one exact Human Decision Gate it dispatches every selected Draft as an independent Direct v501 execution, explicitly calls `Campaigns.suspend`, requires `State=SUSPENDED` before that item writes any child object, submits the exact ad IDs for moderation, and repeats the suspended semantic readback. `Campaigns.resume` is not implemented.

`lib/p0-application.ts` is the authoritative `mox-adv.p0.application` query/command contract for the five-step path. `GET /api/p0` queries the contract and `POST /api/p0` sends a command with `expected_revision`; both local application rendering and future Dashboard rendering consume the returned workflow truth table instead of deriving transitions from document fields. The contract owns the persisted document, including exactly one top-level `analytics_evidence_snapshot`, its reference-only lifecycle ledger, separate `landing_advisory_run`, Campaign Strategy, Recommendation Set, Campaign Draft and external outcome. Queries and restarts reuse the persisted active version and never recompute evidence from a newer provider read. A new evidence result requires an explicit Context/Model/Product Focus/competitor collection command and a new document revision; stale compare-and-swap writers cannot replace the accepted version. A delayed replacement persists an invalidation intent before collection, and migrations reconstruct a verified current-version reference without copying or relabelling the snapshot provenance. Baseline v1/v2/v3/v4 documents migrate their nested snapshot, Context lineage, optional advisory field and provisional one-Draft shortlist into the single v5 document without creating another evidence or Strategy store; content hashes plus persisted questionnaire order and metadata are verified before query reuse or downstream recommendations. Every successful migration or command advances one monotonic document revision through compare-and-swap; the exact package intent and each item dispatch/result checkpoint are CAS-persisted around the separately durable Direct execution journal. `analyze_site` persists provisional Context, and `confirm_context_goal` records the explicit owner decision before full analysis. A material Context edit records the affected Strategy, Recommendation Set, Campaign Draft, shortlist and confirmation lineage, clears those current projections and blocks confirmation until recomputation; normalization-only URL/whitespace changes do not create false invalidation. Evidence and scoring returned for a revision come from that persisted document rather than being recomputed during a query. Legacy application documents are upgraded only when their lineage can be reconstructed; malformed, unknown-schema or orphaned-outcome documents fail explicitly without being overwritten. Public research uses credential-free GET, manual redirects, DNS/IP checks, exact host allowlists for competitor pages and fail-closed redirect/SSRF/size limits. Snapshot, client and persisted artifacts redact credential and common PII patterns; no prompt, token, browser-cabinet data or model chain of thought belongs in the document. Production Wordstat collection uses the separate server-side `YANDEX_WORDSTAT_OAUTH_TOKEN` and registered `YANDEX_WORDSTAT_CLIENT_ID`, plus explicit comma-aligned `YANDEX_WORDSTAT_REGION_IDS`/`YANDEX_WORDSTAT_REGION_NAMES` and `YANDEX_WORDSTAT_DEVICE`; only `POST` calls to `api.wordstat.yandex.net` are allowed, and credentials never enter the batch or client state.

`lib/campaign-viability.ts` is the authoritative `viability-score/1.0.0` comparative contract. It evaluates hard eligibility and required `EVIDENCE_GAP` before dimensions, score, rank or hiding. Eligible Drafts receive `COMPARATIVE PRELAUNCH PRIORITY / NOT A PREDICTION` with exact weights: demand 18%, cost 12%, economics 20%, offer–audience fit 18%, Direct feasibility 12%, measurement readiness 10% and evidence quality 10%. An optional unknown makes its dimension a disclosed midpoint 50 and sensitivity recomputes unknown dimensions at 0/100 while known dimensions remain fixed. Exact score ties share rank only inside one immutable Recommendation Set revision and capability cohort. Score hiding requires sensitivity upper bound `<45`, evidence quality `>=60` and no unresolved required gap; structural reasons always win. Results persist contributions, bounded claim/evidence pointers, exact frequency/cost scopes, blockers, gaps, cohort/comparable-set IDs and all threshold gates. `LandingAdvisoryRun`, moderation/campaign outcomes, post-launch metrics, outcome learning and calibration are excluded from eligibility, dimensions, score, sensitivity, rank, hiding and score/publish fingerprints. Hard-blocked and evidence-gap Drafts remain reviewable but never enter shortlist or confirmation.

The Campaign Canvas renders the exact persisted Recommendation Set as keyboard-openable ranked cards with deterministic variant/evidence filters, rank/score ordering and explicit hidden-candidate audit reasons. Cards keep comparator/improvement, comparative score and semantic ties, sensitivity, evidence quality, scoped Wordstat frequency, one source-labelled pre-launch cost and publish blockers separate. Its modal right drawer consumes the persisted `direct-v501-draft-field-registry-v1`: every campaign, ad-group, explicit criterion, text-ad and current asset-capability field is classified as editable, fixed by Strategy, fixed by capability or conditionally not present. Only the canonical registry's six core fields are enabled, and the client derives its submission membership from that validated persisted registry; each field is validated server-side and round-trips into the exact Direct projection. Queries reject any same-schema registry content drift before UI rendering, while only a genuinely absent legacy registry is migrated; unknown fields fail closed. A canonical no-op reports that normalization created no Draft revision. A material edit creates the next immutable Draft revision and publish fingerprint, records safe previous/current values for every changed Direct pointer, and fully rescored/reranks the fixed membership with dimension, score, rank and concise policy deltas. The `mox-adv.p0.application` `1.14.0` contract also accepts an explicit recommendation recalculation against an injected governed playbook release. It compares exact active-release status, ID, version, digest and applied rule ID/version/digest/eval lineage independently from owner Draft revisions: unchanged lineage preserves the Recommendation Set, every Draft revision and all downstream decisions byte-for-byte, while a real change, expiry or rollback regenerates and invalidates downstream state. The bounded operator-facing `Рекомендация пересчитана` notice matches replacements by stable delivery/capability/variant semantics, reports unmatched additions/removals truthfully and never includes evaluator traces. The typed owner journey shows only the applied business practice and its limitation; release identities, hashes and evaluator diagnostics remain outside the owner response.

`lib/campaign-decision-gate.ts` defines the authoritative ordered shortlist, immutable package review and Human Decision Gate persisted inside `p0-application-document-v11`. Card add/remove/positional-restore commands accept only a Draft choice and recompute exact Draft revision, publish fingerprint, Strategy revision, capability profile and Recommendation Set lineage server-side under document CAS. Hidden, hard-blocked and unresolved evidence-gap Drafts fail closed. The sticky Canvas footer renders the persisted ordered selections independently of display filters and opens a server-built, content-addressed package review containing exact Direct account/capability binding and Analytics Evidence Snapshot identity. Exact-token confirmation stores one content-addressed durable decision and timestamp for that reviewed authority; it performs no Direct call and explicitly states that later campaign dispatch, containment, moderation and evaluation are independent rather than one atomic transaction. Material Context, Model, Strategy, Draft, account/capability/evidence or playbook changes invalidate review and Gate with a bounded content-addressed reason, while normalization-only Draft saves and client-only filters preserve them. Same-schema shortlist, review and confirmation drift is rejected before query rendering. `lib/campaign-package-execution.ts` seals one non-atomic package journal with ordered per-item identities and independent ownership/containment outcomes; `dispatch_package` revalidates the exact Gate, current account and capability lineage before persisting any dispatch intent. The legacy single-Draft `confirm_creation` path remains unavailable from the truth table and UI.

## Deterministic production-candidate E2E

`npm run test:e2e` starts a clean localhost-only P0 runtime with no copied `.env` files or `YANDEX_*` variables and drives all five steps through Playwright at exactly `1920×1080`. The browser never calls the application API directly or manipulates state. The fixture backend remains unreachable on non-loopback hosts, uses official-shape Direct and Wordstat responses, and renders an explicit fixture banner so controlled evidence cannot be mistaken for live data. The flow covers Context/goal, Model and evidence disclosure, LandingAdvisoryRun, the fixed Strategy questionnaire, Campaign Canvas filters and keyboard drawer, a material Draft edit, stale-tab CAS rejection, two-item shortlist/package Gate, independent accepted/rejected moderation, focused correction, renewed Gate and `PASS_AFTER_CORRECTION`. It also checks browser egress, accessibility labels, console/page errors and horizontal overflow. The checked-in machine-readable golden is [`tests/fixtures/production-candidate-acceptance.json`](tests/fixtures/production-candidate-acceptance.json); set `UPDATE_P0_E2E_ACCEPTANCE=1` only when intentionally accepting a changed lineage or provider journal.

The browser flow complements, rather than replaces, the contract matrix in `p0-application-contract.test.mjs`, `direct-write.test.mjs` and `execution-safety.test.mjs`. Those suites cover all-success, mixed provider outcomes, pending and `PREACCEPTED`, unknown/reconciliation, system failure, account single-writer, durable dispatch/restart, duplicate prevention and correction. Ordinary CI runs only controlled fixtures: it loads no production credential, contacts no Yandex or public-research endpoint, never calls `Campaigns.resume`, and starts no spend.
